# ML: поиск товаров под сумму кредита

Модуль `smart_credit_ml.product_search` ищет в интернете товары по ключевым словам. В подборку попадают только те, что укладываются в сумму кредита. Пример: предприниматель берёт 1,5 млн ₽ на оборудование и видит реальные предложения магазинов, которые можно купить на эти деньги.

## Как устроено

```
ключевые слова + сумма кредита
        │
        ▼
 Qwen 3.5 (Ollama) ── составляет 1–3 поисковых запроса
        │
        ▼
 SearXNG ── настоящие ссылки и сниппеты из поисковиков
        │  (дубликаты и utm-метки убираются, не больше 3 ссылок с одного сайта)
        ▼
 загрузка страниц ── schema.org Product / microdata / og:price: цена из разметки
        │  (только публичные адреса, редиректы проверяются, до 1,5 МБ на страницу)
        ▼
 каталоги ── страница со списком товаров (ItemList) заменяется карточками из списка,
        │    у каждой своя ссылка и цена; сама ссылка на каталог в подборку не попадает
        ▼
 Qwen 3.5 ── решает, карточка ли это товара, подходит ли он, какая цена указана
        │
        ▼
 дубли ── один товар одного магазина остаётся один раз, с меньшей ценой
        │
        ▼
 фильтр: цена ≤ суммы кредита → offers; дороже → overBudget (до 3 штук для справки)
```

Почему не «попросить модель найти ссылки». Языковая модель не ходит в интернет. Ссылки, которые она пишет по памяти, выдуманы или давно мертвы. Поэтому:

- **URL пишет только поисковик.** Модель отвечает номером результата, а ссылка берётся из этого результата. Номер, которого не было в выдаче, отбрасывается.
- **Цену из разметки страницы модель не трогает.** Если разметки нет, цена, названная моделью, принимается только когда это же число есть в тексте страницы или в сниппете. Иначе предложение уходит в `stats.noPrice`.
- **Валюта.** Цена из разметки в другой валюте не считается рублями.
- **Каталоги.** Поисковики на запрос «купить … цена» отдают в основном страницы категорий. Страница считается каталогом, если в её разметке есть ItemList с несколькими товарами, несколько разных товаров на верхнем уровне или несколько блоков microdata Product. У каталога нет своей цены: из него берутся карточки (не больше 10 с одной страницы и 40 всего), у которых есть своя ссылка и цена. Ссылка карточки должна вести на тот же сайт. Карточки без ссылки отбрасываются, ссылка на сам каталог не выдаётся никогда, даже если модель сочтёт его товаром.
- **Дубли.** Одна и та же ссылка, найденная в двух каталогах или и в поиске, и в каталоге, берётся один раз. Один и тот же товар одного магазина под разными ссылками (совпадает название без учёта регистра, пунктуации и «ё») остаётся один раз, с меньшей ценой. Одинаковые товары в разных магазинах — разные предложения.
- **Источник цены** виден в поле `priceSource`: `structured` (разметка страницы товара), `catalog` (разметка карточки в каталоге), `page_text` (текст страницы, проверено), `snippet` (сниппет поисковика, проверено).
- **Без модели.** Если Ollama недоступна, модуль ищет по самим ключевым словам и оставляет только страницы с ценой в разметке schema.org. Об этом сообщает `warnings`.

Модель — Qwen 3.5 с открытыми весами, этого требует кейс. Поисковик — SearXNG в своём контейнере. Платных API нет.

## Запуск

Всё сразу, из корня репозитория:

```bash
docker compose up --build ml
```

При первом старте `ollama-pull` скачивает модель (`qwen3.5:4b`, около 3 ГБ) в том `ollama-data`. Модель меняется переменной `ML_LLM_MODEL` в корневом `.env`.

Проверка:

```bash
curl -X POST http://localhost:8000/product-search -H "Content-Type: application/json" -d "{\"keywords\": \"холодильная витрина\", \"budgetRub\": 500000, \"purpose\": \"Покупка оборудования\"}"
```

Swagger: http://localhost:8000/docs

Локально без Docker для ML-сервиса (Ollama и SearXNG при этом запущены, например через compose):

```bash
cd src/ml
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[test]"
.venv/Scripts/smart-credit-products "холодильная витрина" 500000 --purpose "оборудование"
.venv/Scripts/uvicorn smart_credit_ml.api:app --port 8000
```

## API

Сервис слушает порт **8000**: это адрес `Ml:BaseUrl` в `src/backend/appsettings.json`. В Compose бэкенду передаётся `Ml__BaseUrl=http://ml:8000`.

### `POST /` — передача заявки от бэкенда

Этот запрос шлёт `PurposeHandoff.cs` на этапах проверки по реестрам и скоринга:

```json
{
  "applicationId": 42,
  "amount": 500000,
  "category": { "matches": [
    { "code": "laptop", "title": "Ноутбук", "keywords": ["ноутбук"] },
    { "code": "mfu", "title": "МФУ", "keywords": ["мфу"] }
  ] }
}
```

Бэкенд ждёт ответ 3 секунды и читает только код ответа, а поиск идёт минуты. Поэтому сервис сразу отвечает `202 Accepted` с `{"applicationId", "status", "results"}` и ставит задание в очередь. Фоновый воркер выполняет задания по одному: Ollama всё равно держит одну модель. По каждой категории, не больше трёх (`ML_HANDOFF_MAX_CATEGORIES`), он ищет её название (`title`) с бюджетом, равным сумме кредита.

Статусы задания:

| `status` | |
|---|---|
| `queued` | принято, ждёт воркера |
| `running` | идёт поиск |
| `done` | поиск прошёл хотя бы по одной категории |
| `failed` | ни одна категория не нашлась: поисковик недоступен или упал поиск |
| `no_categories` | бэкенд не распознал в цели ни одного товара, искать нечего |

**Повторы.** Бэкенд повторяет передачу, если не получил 2xx. Задание в статусе `queued`, `running` или `done` при повторе не перезапускается. Задание в статусе `failed` запускается заново. Задания, оставшиеся `queued`/`running` после остановки сервиса, при старте снова ставятся в очередь.

Задания хранятся в базе `ml`, в таблице `ml.goods_searches` (`sql/002_goods_searches.sql`). Сервис создаёт её при старте, если таблицы нет. `ML_GOODS_STORE=memory` держит задания в памяти процесса, это удобно для запуска без Postgres.

### `GET /applications/{id}/goods` — результат поиска по заявке

Ответ: `applicationId`, `amount`, `status`, `categories` (как прислал бэкенд), `error`, `updatedAt` и `results[]`. В каждом элементе `results`: `code`, `title`, `keywords` и либо `search` (ответ в формате `/product-search`), либо `error`. Для неизвестной заявки ответ 404.

### `POST /product-search` — один поиск сразу

| Поле | Тип | |
|---|---|---|
| `keywords` | string, 2–200 | что купить |
| `budgetRub` | number > 0 | сумма кредита |
| `purpose` | string? | цель кредита, помогает составить запросы |
| `maxResults` | int 1–30, по умолчанию 10 | |

Ответ: `queries`, `offers[]` (`name`, `url`, `domain`, `priceRub`, `priceSource`, `relevance` 1–5, `reason`, `query`), `overBudget[]`, `stats` (`candidates`, `fetched`, `catalogs`, `listed`, `duplicates`, `notOffer`, `noPrice`, `overBudget`), `warnings[]`, `searchUnavailable` (ни один запрос к поисковику не выполнился). Подборка отсортирована по релевантности, при равной — по цене.

## Ограничения

- Крупные маркетплейсы (Ozon, Wildberries, DNS) часто не отдают страницу боту. По ним цена берётся из сниппета поисковика, если она там есть.
- Цены в выдаче меняются. Результат по заявке сохраняется один раз и сам не обновляется. Один поиск на `qwen3.5:4b` без GPU занимает от десятков секунд до нескольких минут на категорию.
- Бэкенд передаёт заявку, но результат поиска сам не забирает: `GET /applications/{id}/goods` пока никто не вызывает, и фронтенд подборку не показывает.
- Бэкенд узнаёт категорию по подстроке в цели кредита, поэтому возможны ложные совпадения: «компьютер» находится и в «компьютерный стол».
